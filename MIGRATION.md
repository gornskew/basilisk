# Migrating the yard out of skewed-emacs

Status as of **2026-08-15**: nothing has moved. The framework is fully
working in `skewed-emacs/`. This document is the manifest, written before
any file moves so the move itself is mechanical.

Survey basis: `skewed-emacs` at `devo` HEAD `4f677ed`, with all five stack
overlays converted to symbolic rosters and their generated compose YAML
verified byte-identical.

## The cut

The guiding line: **basilisk owns everything needed to bring a fleet up;
skewed-emacs owns the captain's configuration and the image carrying it.**

Notably this includes the *base* `services.sexp`. That is the part worth
being deliberate about — see "Why the base definition comes too" below.

### Moves to `basilisk/`

| path in skewed-emacs | what it is |
|---|---|
| `compose-dev` | the stack driver, ~1000 lines of POSIX sh |
| `basilisk` | symlink → `compose-dev` (the preferred name) |
| `generate-configs.el` | generator: compose YAML, MCP configs, elisp discovery, install scripts, eyes-only heap probes |
| `generate-env.sh` | `.env` generation, branch detection |
| `fittings.sexp` | the fitting catalogue: posts → container services, crew-levels, probes |
| `services.sexp` | the **base** stack definition (SSoT for the vanilla fleet) |
| `docker-compose.yml` | generated from the above |
| `BASILISK.md` | the naming, the crew, the conceit |
| `systemd/`, `systemd-system/` | unit + installer that bring the stack up at boot |

### Stays in `skewed-emacs/`

| path | what it is |
|---|---|
| `dot-files/` | the Emacs configuration itself — the actual product |
| `setup` | host-side installer for that configuration |
| `docker/` | the image build: `Dockerfile`, `build`, `run`, `skewed-install`, `webshot`, `webshot-clip`, `emacs-repl.sh` |
| `img/`, `windows-keybindings` | image assets, keybinding docs |
| `docs/` | mostly Captain-facing; a few files need a pass (below) |

### Needs splitting, not moving

**`mcp/`** — mixed. `mcp-container.json`, `mcp-windows.json`, `mcp.toml`
and the `narad-stack-*` variants are *generated by* `generate-configs.el`
and describe the whole fleet's backends → yard. `merge-mcp-configs.el`,
`mcp-exec` and `entrypoint.sh` are fleet-level plumbing → yard.
`opening-prompt.md` is Captain-flavored → stays. Decide per file rather
than moving the directory wholesale.

**`README.md` and `CLAUDE.md`** — both currently describe all three
assets. Each wants splitting, with the stack half moving here. The
skewed-emacs README's own three-asset section is the natural seam: it
already makes the argument for this repo existing.

**`docs/`** — `CLAUDE_DESKTOP.md`, `HOST_EMACS_MCP.md`,
`FIRST_SESSION_TRANSCRIPT.md` and `DEMO_GIF.md` all reference
`compose-dev`. Re-point rather than move; they are onboarding docs for
the editor, which happens to arrive via the stack.

### Does not move, and should be deleted or ignored

- `narad-stack-compose.yml` — a **copy** (not a symlink) of narad's
  overlay sitting in the working directory because this dev host is
  narad. It is the documented glob footgun: `_collect_compose_files`
  globs `./*.yml`, so a second host overlay in the same directory would
  merge two fleets silently. Do not carry it here.
- `compose-dev.pre-validation-refactor` — stale backup.

## Why the base definition comes too

`fittings.sexp` marks `:captain`, `:ship-engineers` and `:medic` with
`:in-base t`, meaning "already defined by the vanilla
`docker-compose.yml`, so an overlay emits only the delta." That flag is
an assertion about what the base `services.sexp` contains.

Leave the base behind in `skewed-emacs` and `:in-base` becomes an
unenforced cross-repo invariant — precisely the drift the symbolic
rosters were built to eliminate, reintroduced one level up. Bringing the
base along keeps `:in-base` a statement about a file in the same repo.

The cost is that `basilisk` then contains a definition of the
`skewed-emacs` *service*. That is correct and not a leak: it references
the image by name (`gornskew/skewed-emacs:...`), exactly as it references
`gornskew/cyclops:master`. No repo coupling, only an image reference.

## What breaks, and how much

### External references — 13 sites, all cosmetic or one-line

Every stack overlay's `services.sexp` header carries a regeneration
recipe, and three stack READMEs repeat it:

```
sally-stack/services.sexp:16     (load "/projects/skewed-emacs/generate-configs.el")
shelly-stack/services.sexp:17    (load "/projects/skewed-emacs/generate-configs.el")
elsie-stack/services.sexp:18     (load-file "/projects/skewed-emacs/generate-configs.el")
narad-stack/services.sexp:16     (load-file "/projects/skewed-emacs/generate-configs.el")
balaram-stack/services.sexp:24   (load-file "/projects/skewed-emacs/generate-configs.el")
sally-stack/README.md:36         same
shelly-stack/README.md:36        same
balaram-stack/README.md:42       same
```

Plus five prose mentions of `skewed-emacs/fittings.sexp` in the same
`services.sexp` headers, and one cross-link in `cyclops/README.md:18`
pointing at `../skewed-emacs/BASILISK.md`.

All are comments or documentation. None is executed by the generator.
They become `/projects/basilisk/generate-configs.el` and
`../basilisk/BASILISK.md` in a single sweep.

Note that `skewed-gen-fittings-file` in `generate-configs.el` defaults to
`/projects/skewed-emacs/fittings.sexp` — that one **is** executed and
must change with the move.

### `bootstrap_from_image` — the one genuinely hard problem

`compose-dev:58-95` handles the standalone case: someone curls
`compose-dev` on a bare box with no clone. With no `docker-compose.yml`
beside it, it creates a container from the skewed-emacs image and
`docker cp`s three items out of `/home/emacs-user/skewed-emacs/`:

```
docker-compose.yml    generate-env.sh    mcp/
```

**All three are yard files.** So the skewed-emacs *image* is currently a
delivery vehicle for the framework, and the split breaks that path unless
it is addressed. Three options, in preference order:

1. **Vendor basilisk into the skewed-emacs image** at build time (a
   snapshot under `/home/emacs-user/basilisk/`), and re-point the `docker
   cp` source. Smallest change; keeps one-command standalone bootstrap
   working with no second pull. Costs a build-time dependency from the
   image on this repo.
2. **Bootstrap from a basilisk image.** Cleanest conceptually — the yard
   ships the yard — but means publishing an image whose only job is to
   carry text files, and a second pull on first run.
3. **Fetch from gitlab over HTTPS.** No image involvement, but it needs
   network access to `gitlab.genworks.com` and credentials for a private
   repo, which the current path deliberately avoids.

**DECIDED (Dave, 2026-08-15): option (1)** — vendor a basilisk snapshot
into the skewed-emacs image and re-point the `docker cp` source. Revisit
(3) once the github mirror exists.

### The bare one-liner still has to work

Dave, 2026-08-15: "the one-liner `./basilisk` can come from basilisk now
— that should still work bare."

So the standalone entry point inverts. Today you curl `compose-dev` out
of the **skewed-emacs** repo and it bootstraps its runtime files from the
skewed-emacs image. After the move you curl `basilisk` out of **this**
repo, and it still bootstraps from the skewed-emacs image (option 1
above) — the script comes from the yard, the payload rides in the
Captain's image.

That is a coherent split rather than an accident: the image is a
convenient, already-published, already-pulled carrier, and the standalone
user is about to pull it anyway. It does mean the vendored snapshot must
stay fresh, so the image build should copy basilisk in at build time
rather than anyone hand-syncing it.

Acceptance test for this path, worth writing down because it is the one
users hit first and the one nobody runs by accident:

```
mkdir /tmp/bare && cd /tmp/bare
curl -O <basilisk raw URL>/basilisk && chmod +x basilisk
./basilisk up
```

must bring a stack up in an empty directory with no clone of anything.

Also note the error message at `compose-dev:66` points at
`https://github.com/gornskew/skewed-emacs` as the fallback clone
instruction. It will want to name this repo — at its **gitlab** URL,
since the github mirror does not exist yet — once the yard lives here.

## STATUS 2026-08-15: phase 1 done — machinery populated and verified

The yard is now **copied** into this repo and proven to work from here.
Nothing has been removed from `skewed-emacs`, which is still fully
functional and untouched.

**Sequencing (Dave):** *"Once basilisk is populated with ostensibly
working machinery, I think we just rip any stack-related stuff right out
of skewed-emacs and direct the reader of any READMEs to basilisk as the
slipperiest path to getting a skewed-emacs container spun up."*

Copy-then-verify-then-rip, rather than the `git mv` this document
originally proposed. It is the safer order and it is also the only one
that actually works across two separate repositories: at no point is the
stack unbootable, and the removal step becomes trivial once the
replacement is known good.

**Branch:** this repo tracks `devo`, for parity with `skewed-emacs` and
`lisply-mcp`. (`eyes-only` stays on master/main "in raw-dogging
tradition until anybody actually starts buying this stuff".)

Regenerated all five host stacks plus the base from **this** repo's
`generate-configs.el`:

| output | result |
|---|---|
| sally / shelly / balaram / elsie / narad overlay compose | **byte-identical** |

### Two changes the move required

1. **`skewed-gen-fittings-file` now resolves beside the loaded generator**
   instead of being hardcoded to `/projects/skewed-emacs/fittings.sexp`,
   and is `setq`'d at load time rather than left to `defvar`.

   The `defvar` part is not pedantry — it bit immediately. A `defvar`
   default is evaluated only on the first load in a session and then left
   alone (exactly the property eyes-only's `parameters.lisp` depends on
   to survive hot reloads). With two copies of the generator side by side
   during the move, a session that had loaded skewed-emacs's copy kept
   pointing at **skewed-emacs's catalogue** after loading this one, and
   generated from the wrong repo with nothing in the output to say so.
   Caught by asserting the resolved path rather than trusting it.

2. **Base-name handling.** `basilisk` joins `skewed-emacs` as a name that
   means "this is a base, not a host overlay" — so it generates an
   unprefixed `docker-compose.yml`, and does not get an overlay `install`
   script (a base repo is what you run the stack *from*, not something
   you install into another checkout).

### Entanglements found while doing it, not visible from the survey

- **`compose-dev` uses `SCRIPT_DIR="$(pwd)"`, not the script's own
  location.** It must be run from the directory holding
  `docker-compose.yml`, `generate-env.sh`, `mcp/` and `dot-files/`. That
  is fine once the yard lives here, but it means `./basilisk` is not
  runnable from an arbitrary directory, and the bare-one-liner story
  needs to account for it.
- **The generator writes into `dot-files/`.** `services-generated.el` is
  yard *output* but lands in the Captain's configuration tree
  (`dot-files/emacs.d/etc/`), which this document assigns to
  `skewed-emacs`. Both repos now contain a copy. **Unresolved:** either
  the yard owns that path (and skewed-emacs's copy becomes stale), or
  generation targets a location the Captain's config reads from. Decide
  before the rip, because it determines what `dot-files/` means.
- **`compose-dev` also reads `mcp/` and expects `.git` beside it**, which
  is why `mcp/` came across wholesale rather than per-file. The per-file
  split proposed above is still the right end state and is still pending.

## Suggested order

1. Land this manifest (done — you are reading it).
2. `git mv` the unambiguous yard, fix `skewed-gen-fittings-file`, sweep
   the 13 external references, regenerate all five stacks and **diff the
   generated compose YAML — it must come out byte-identical.** That diff
   is the acceptance test for the whole move; it is what proved the
   symbolic-roster conversion correct and it works just as well here.
3. Split `mcp/`, then `README.md` / `CLAUDE.md`.
4. Fix `bootstrap_from_image`, and rebuild the skewed-emacs image if
   option (1) is chosen.
5. Only then update the public site — pointing readers at a Basilisk with
   no repo of its own would be the wrong order.

## Deliberately not in scope

The stack's *behavior* does not change here. Symbolic rosters, crew
levels, the recommended-Captain rule, roster-derived heap probes and the
`eskew`/`egskew` messages all landed in `skewed-emacs` before this split
and move across as-is. If the compose YAML changes, something went wrong.

(The Captain rule was briefly stricter — the generator *refused* a roster
without `:captain`. Revised the same day: it warns and proceeds, because
a Pilot-only roster is a standalone Cyclops deployment and an
engineer-only roster is a standalone monolithic KBE server, and both are
shapes we ship. Only `skewed-network` is structurally required.)
